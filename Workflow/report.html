1. Executive Overview

Lumex is a full-featured academic research publishing platform designed to handle the complete lifecycle of scholarly communication — from manuscript submission and peer review through editorial decision-making, publication, and reader access. The platform supports multiple user roles (Reader, Author, Reviewer, Editor, Admin), implements dual publishing workflows (legacy paper system + modern submission pipeline), and integrates AI-powered paper summarization.

Key Capabilities

  • Multi-Role System: 5 roles (READER, AUTHOR, REVIEWER, EDITOR, ADMIN) with granular permissions
  • Dual Submission Workflows: Legacy paper system + modern 8-state submission pipeline
  • Peer Review: Editor assigns reviewers, structured review form, editorial decision system
  • Publishing: Journals, books, chapters, collections, special issues, conferences
  • AI Integration: PDF summarization and Q&A using Groq (Llama 3.3 70B)
  • Payment System: Article purchase and APC (Article Processing Charges) checkout
  • Search: Full-text search with faceted filtering and suggestions
  • Email Notifications: 19 automated email templates via Resend
  • Alert System: Keyword/journal/discipline alerts with batch digest delivery

4.3 Request Lifecycle & Middleware Pipeline

HTTP Request │ ▼ 1. cors() → CORS headers 2. helmet() → Security headers (XSS, CSP, etc.) 3. morgan("dev") → Request logging 4. express.json() → Parse JSON body 5. globalLimiter → 200 req / 15 min / IP │ ▼ Route-specific limiters (authLimiter: 10/15min, searchLimiter: 60/1min, etc.) │ ▼ authenticate → Verify JWT, set req.user = { userId, role } │ ▼ requireRole(...roles) → Check role, 403 if unauthorized │ ▼ Controller → Zod.safeParse(body), call service │ ▼ Service → Business logic, Prisma queries, cache, email │ ▼ sendSuccess(res, data) → Standard JSON envelope response │ Any Error → errorHandler → AppError (statusCode + message) or 500

5. Frontend Architecture

5.1 Feature-Sliced Design (FSD)

The frontend follows the Feature-Sliced Design architectural pattern, organizing code into strict layers with a one-way dependency flow:

Pages ← Top-level route components (27 page directories) │ ▼ Widgets ← Complex UI composition blocks (23 widgets) │ ▼ Features ← Business logic & user interactions (11 feature groups) │ ▼ Entities ← Domain objects & data (10 entity types) │ ▼ Shared ← Reusable UI, API, hooks, types, utils (26+ components)

Rule: Each layer may only import from layers below it. Pages import Widgets, Widgets import Features, etc.

5.4 API Layer & Fallback Pattern

The frontend uses a unique fetchWithFallback pattern for development flexibility:

async function fetchWithFallback<T>(
  endpoint: string,          // e.g. "/articles"
  fallbackJsonPath: string,  // e.g. "/mock-data/articles.json"
  options?: RequestInit
): Promise<T>

// 1. Tries real API call:  GET /api/articles
// 2. If fails (network error, 4xx, 5xx):
//    Falls back to:        GET /mock-data/articles.json
// 3. Returns typed data either way

This allows the frontend to function even without the backend running, using static JSON files in /public/mock-data/.
